## What the Last Call text changed

The header status is Last Call. The header has no `Last-Call-Deadline` field. KCC-0, which is Final, says a KCC editor sets that date when assigning Last Call, typically 14 days later, and the header table says the field is required when status is Last Call. KCC-1 and KCC-2 on the same commit also say Last Call and also omit the field. KCC-20 `Requires` KCC-1 and KCC-2. KCC-0 says a Standards Track KCC moves to Final only after a completed Last Call, and only when every required KCC is itself Final.

The borrowed-receive prose now defines the effective threshold as `max(decoded_threshold, 0)`. The increase must be strictly greater than that value. Negative payloads behave as zero. The complete `borrow_guard` stays as stored. A contract may still require a non-negative payload. The abbreviated vectors add the zero, negative, negative-zero, and guard-preservation cases. The reference actor already did this: `contracts/kcc20.ag` clamps a negative threshold to 0, requires `amount_increase > amount_threshold`, and on the threshold path keeps `next_borrow_guard` equal to the stored guard.

The document links [argent-lang/kcc20-reference](https://github.com/argent-lang/kcc20-reference). An implementation may limit the total input token amount to `2^63 - 1`. The reference README says totals must fit in `2^63 - 1`.

Borrow schemes stay exclusive bytes: `0x00` disabled, `0x01` amount-threshold, `0x02` schnorr, `0x03` hash-chain. The hash-chain witness is 129 bytes: next guard, one-time public key, signature. The check is `Hash(revealed_guard || one_time_pubkey) == borrow_guard`, with `Hash` the KCC-1 unkeyed BLAKE3.

Section 2 still says a delegator validates only its local owner, and that the leader validates the complete transition. The same section says both entrypoints must follow KCC-1 section 3.8.1. That section puts authentication of every program, template, or state on the leader. A delegator's extra local checks are whatever the protocol needs in order to rely on the leader. KCC-1 also describes one implementation in which the leader authorizes the outputs and each delegator checks that its own authorized-output count is empty.

The name `P2PKHHash` is still in section 3 and in the two example lines. KCC-2 calls the same value `Hash(public_key)` and says it is unkeyed BLAKE3 over the raw public-key bytes. KCC-2 does not define the name `P2PKHHash`. Recomputed here:

```text
blake3(22^32)       = 7caa514a05535fd97887e483ce6f1fc36ef7026435c47521b04549d9af4837bf
blake3(02 || 55^32) = ed887ad164d313eeeac970912504a81156274732ab09c0c0559ff59160abddf9
```

Those are the two digests printed in `kcc-0020.md`, and they are the `p2pkh_hash_hex` values in the reference conformance fixture. The reference function is `p2pkh_hash`, which returns `blake3(public_key)`.

## Inconsistencies

1. The 7 Oct page on this repo still says Draft at `411b41bc` and an open pull at `72767847`. `kcc-0020.md` is Last Call at `3fbec524`. The reference master is `c8a08711`, same tree as `0175e2de`.
2. KCC-0 requires `Last-Call-Deadline` when status is Last Call. The KCC-20, KCC-1, and KCC-2 headers on `3fbec524` omit it. Final also waits on KCC-1 and KCC-2 being Final.
3. The spec still writes `P2PKHHash`. KCC-2 writes `Hash(public_key)`, unkeyed BLAKE3. The example digests match that function. The name is the leftover.
4. Section 2 says the delegator validates only its local owner. The merged generated delegator also reads the leader with `readInputStateWithTemplate` of the KCC20 template. KCC-1 puts the full template check on the leader and leaves extra delegator checks to the protocol. The generated read is such an extra check, and the spec sentence does not say it.
5. Post 74's 3090-byte reference row matches his `KCC20Ref.json` (span length 112, `readInputState`). The merged public-mint KCC20 script is 4031 bytes with span length 145. His fee cells are measurements of his scripts. His P2 allowlist slice starts at 113. The merged span is 145.
6. The six-field encoding in the spec is 112 bytes. The merged script state span is 145 bytes. Publishing either number as the other one welds two layouts.
7. Post 59's bit flags, the `else` on the last arm, and the bare `Hash(borrow_witness)` check are a different borrow rule from the exclusive bytes and the 129-byte one-time key in the Last Call text.
8. `kcc20.json` is silent on the 32 zero-byte commitment that `public_mint.rs` calls this deployment's fixed extension identity. Section 4's description duty applies when a covenant defines extended state. This deployment stores the field and publishes no extended-state type.
9. His README still calls the standard a draft. The kccs header says Last Call.

## What I would do

1. Put `Last-Call-Deadline` on KCC-20, and on KCC-1 and KCC-2, before treating the window as open. KCC-0 says a normative change during that window returns the document to Review.
2. Replace the name `P2PKHHash` with `Hash(public_key)`. Leave the two digests. They already match unkeyed BLAKE3.
3. Say in the reference README that the generated delegator reads the leader with the KCC20 template, so a second template in the same covenant fails that read. The section 2 sentence does not say this. KCC-1 leaves the extra check to the protocol. If a batch leader is wanted, the holder has to name that second template. The merged script names only its own. Ross's P2 names a second template, and it is a different program with a 112-byte span.
4. Print the compiled size next to `kcc20.json`: KCC20 redeem script 4031 bytes, state span offset 1 length 145, template hash `9703112ee6e3555107cd168858992b77d3b74f655205b2b463b1f9ec2ec73cf7`. The 3-in / 3-out bound is inside that script, and the script rides in the signature script of every later transfer. His cost point is about a 3090-byte program.
5. Keep 112 and 145 apart in every note. 112 is the six-field record. 145 is this script's state span.
6. Add one sentence to `kcc20.json`: this deployment's commitment is 32 zero bytes, the actor checks equality, and it defines no extended-state type. The code comment already says the first half.
7. Leave the August bit-flag sketch out of the borrow byte. A combined guard needs a layout the 32-byte field was not given, and the sketch's `else` rejects every borrow that omits the hash-chain bit.
8. Finish the split and reclaim conformance suite before treating `PublicMint` as covered by the transfer vectors. The transfer suite and the mint entry are different programs.
9. When quoting post 74's fees, name his artifact. A 4031-byte script is a different mass from a 3090-byte script. This desk did not recompute the KAS cells.
